# SprintOS Do Not Build Next

## Principle
SprintOS does not need more breadth right now. It needs stronger focus, simpler presentation, and a cleaner main lane.

## Do Not Build Yet

### Deployment automation
Why premature:
- The current problem is not missing deployment power.
- Automating deployment would add high-risk complexity to a product already exposing too many operational concepts.
- SprintOS should first make local release candidates calmer and clearer.

### GitHub automation
Why premature:
- Repo creation, branch management, PR creation, and sync workflows would turn SprintOS into a repo operations console.
- The current product should stay focused on local artifact preparation and handoff clarity.

### More AI providers
Why premature:
- AI routing is already complex relative to current UX clarity.
- More providers would increase settings burden, diagnostics burden, and testing surface without solving the core UX issue.

### More dashboards
Why premature:
- SprintOS already has a Today Dashboard plus a Project Command Center.
- Additional dashboards would deepen the exact fragmentation currently causing confusion.

### More artifact types
Why premature:
- The current artifact chain is already broad.
- Additional artifact categories would create even more nouns, buttons, and report clutter.

### Public SaaS features
Why premature:
- SprintOS is explicitly local-first and single-user oriented.
- Public multi-user surfaces would distort both the architecture and the product philosophy.

### User accounts
Why premature:
- Accounts would add auth, session handling, and UI complexity that does not help the current personal-use product.

### Billing
Why premature:
- Billing solves no current user problem.
- It would push SprintOS toward a business platform identity before the core product is simple enough.

### Cloud sync
Why premature:
- It conflicts with the strongest current product quality: local-first safety and independence.
- Sync would add state conflict, secret handling, and trust complexity.

### Advanced analytics
Why premature:
- SprintOS already produces enough metadata to distract from action.
- Analytics would increase reporting weight instead of improving momentum.

### Complex settings systems
Why premature:
- The app already exposes too many configurable surfaces.
- A larger settings model would worsen the "control panel" feeling.

## What To Build Instead
- Simpler first-open flow
- Stronger single-action guidance
- Cleaner project-stage sequencing
- Better naming
- Less visual and conceptual noise

## Litmus Test For Future Ideas
Only build a new capability if it clearly does one of these:

- reduces visible choices
- shortens time to first useful artifact
- improves local safety
- makes the next step more obvious

If it does not pass that test, it should wait.
